PROJECT ARCHITECTURE + CGI INTEGRATION GUIDE

Goal
- Explain how this webserv is organized.
- Explain how to integrate the existing CGI module into the request/response flow.

==================================================
1) High-level architecture
==================================================

The server is split into 4 main parts:

1. Config parsing
- Files: server_core/ConfigFileParser/parser.hpp, parser.cpp
- Responsibility:
	- Parse config.conf into C++ structs.
	- Fill Server and Location objects.

Main structs:
- Server:
	- interface_ip, port, root
	- locations (vector<Location>)
	- error_pages, max_body_size
- Location:
	- path, root
	- methods, redirection
	- directory_listing, default_file
	- upload_enabled, upload_path
	- cgi_extension, cgi_path


2. Event loop + network I/O
- Files: server_core/server_core.hpp, server_core/server_core.cpp, server_core/server.cpp
- Responsibility:
	- Open listening sockets for all configured servers.
	- Accept clients.
	- Read data with poll() + recv().
	- Build HttpRequest and HttpResponce per complete HTTP message.

Flow:
- main() -> parser(...) -> Server_core::server_init() -> Server_core::server_starting()


3. Request parsing
- Files: request-responce/HttpRequest.hpp, HttpRequest.cpp
- Responsibility:
	- Parse request line, headers, body.
	- Support Content-Length and Transfer-Encoding: chunked.
	- Expose parsed data with getters used by response and CGI.


4. Response generation
- Files: request-responce/HttpResponce.hpp, HttpResponce.cpp
- Responsibility:
	- Match location.
	- Validate method.
	- Process GET/POST/DELETE.
	- Build final raw HTTP response string.

Current behavior:
- Static files: supported.
- Directory listing: supported.
- Upload/delete: supported.
- Redirection: supported.
- CGI: NOT integrated yet into this class flow.


5. CGI module (already implemented, not wired)
- Files: cgi/cgi.hpp, cgi/cgi.cpp, cgi/env_builder.cpp
- Responsibility:
	- Build CGI environment variables from request.
	- Fork child process.
	- execve() CGI interpreter + script.
	- Send request body through stdin (POST/PUT).
	- Read CGI output from stdout.
	- Return raw output + exit status.

API available:
- cgi_result exeute_cgi(HttpRequest& req, Server& ser, Location& loc, std::string client_ip)

==================================================
2) What is missing today for CGI integration
==================================================

Not yet connected points:

1. Build system
- Makefile does not compile cgi/cgi.cpp and cgi/env_builder.cpp.

2. Response logic
- HttpResponce::proccess() does not detect CGI requests.
- No call to exeute_cgi(...).
- No parser for CGI output headers/body before building final HTTP response.

3. Optional data source
- Client IP is not currently passed into HttpResponce.
	(CGI currently needs a client_ip string parameter.)

==================================================
3) Integration plan (recommended)
==================================================

Step 1: Add CGI sources to build
- Edit Makefile SRC list:
	- add cgi/cgi.cpp
	- add cgi/env_builder.cpp


Step 2: Add CGI detection in HttpResponce
- Add a helper in HttpResponce:
	- bool isCgiRequest() const;

Suggested logic:
- CGI is enabled when location has:
	- _location.cgi_extension not empty
	- _location.cgi_path not empty
- Request path contains cgi_extension (example: ".py", ".php").


Step 3: Execute CGI before static handlers
- In HttpResponce::proccess(), after location/method/body validations and before HandleGet()/HandlePost()/HandleDelete(), do:
	- if (isCgiRequest()) HandleCgi(); return;


Step 4: Implement HandleCgi()
- New method in HttpResponce:
	- void HandleCgi();

Inside HandleCgi():
1. Call exeute_cgi(req, server, _location, client_ip)
2. If child exit code != 0 and output invalid, set 500.
3. Parse CGI raw output into:
	 - CGI headers block
	 - CGI body
4. If CGI output contains "Status:" use it as HTTP status.
5. If CGI output contains "Content-Type:" use it.
6. Set fileContent/body and fileSize.

Note:
- Classic CGI output usually looks like:
	Content-Type: text/html\r\n
	\r\n
	<html>...</html>


Step 5: Keep response builder compatible
- Existing craftResponce() can still produce final HTTP wire format.
- Just make sure HandleCgi() sets:
	- status_code / status_message
	- contentType
	- fileContent
	- fileSize

==================================================
4) Minimal pseudocode (for friend)
==================================================

In HttpResponce::proccess():

if (!validateLocation()) 404
if redirection set -> 301
if method not allowed -> 405
if body too large -> 413

if (isCgiRequest()) {
		HandleCgi();
		return;
}

if method == GET -> HandleGet()
if method == POST -> HandlePost()
if method == DELETE -> HandleDelete()


In HandleCgi():

cgi_result res = exeute_cgi(req, server, _location, "127.0.0.1"); // temporary client ip
if (res.exit_status != 0) -> 500
parse headers/body from res.raw_output
set contentType/status/body


==================================================
5) Config usage for CGI
==================================================

Your parser supports this directive inside location block:

cgi <extension> <interpreter_path>;

Examples:
- cgi .py /usr/bin/python3;
- cgi .php /usr/bin/php-cgi;

Example location:

location /cgi-bin {
		methods GET POST;
		root ./www/site1;
		cgi .py /usr/bin/python3;
}

How it should behave:
- Request /cgi-bin/test.py -> CGI mode.
- Request /images/a.png -> static mode.

==================================================
6) Test checklist after integration
==================================================

1. Build
- make re

2. GET CGI script
- curl -i "http://127.0.0.1:8080/cgi-bin/test.py?name=alice"

3. POST CGI script
- curl -i -X POST "http://127.0.0.1:8080/cgi-bin/test.py" -d "x=10&y=20"

4. Validate headers
- Check Content-Type from CGI is forwarded correctly.

5. Validate failures
- Broken script/interpreter should return 500.


Summary
- The project already has a good CGI execution module.
- Main missing work is wiring it into HttpResponce flow and adding CGI files to Makefile build.
- Once those two are done, CGI can run with config-based control per location.
